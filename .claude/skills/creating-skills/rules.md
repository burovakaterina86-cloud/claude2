## Описание

Claude видит заранее только `name` и `description` каждого скилла и по описанию выбирает нужный, возможно из сотни. Описание без «когда» - причина, почему скилл то вызывается, то нет.

- Две части: что делает и когда применять. Во второй части слова, которыми человек об этом попросит.
- От третьего лица. Описание встраивается в системный промпт, смена точки зрения мешает находить скилл.
- До 1 024 символов, без XML-тегов, не пустое. В Claude Code `description` вместе с `when_to_use` обрезается на 1 536 символах, поэтому главный сценарий пиши первым.
- Плохо: «Помогает с документами», «Обрабатывает данные». Хорошо: «Извлекает текст и таблицы из PDF, заполняет формы, объединяет документы. Применять, когда пользователь упоминает PDF, формы или извлечение данных из документов».
- Скилл с `disable-model-invocation: true` вызывается только вручную через `/имя`, его описание в контекст не попадает. Тогда «когда применять» в описании не обязательно.

## Размер и структура

- `SKILL.md` короче 500 строк. При вызове он целиком ложится в контекст.
- `SKILL.md` - оглавление и главный порядок работы. Справочник, примеры, шаблоны - в файлы рядом, их Claude читает только когда нужно.
- Скилл про несколько областей: по файлу на область. Вопрос про продажи тогда не загружает маркетинг.
- Файлам давай говорящие имена: `form_validation_rules.md`, а не `doc2.md`.

## Ссылки между файлами

- Все файлы упомянуты прямо в `SKILL.md`, с пометкой, когда читать. Если Claude никогда не открывает файл, значит либо он не нужен, либо на него плохо указано.
- Один уровень: `SKILL.md` -> файл. Файл, до которого Claude дошёл по ссылке из другого файла, он склонен читать частично (например `head -100`) и получит неполные сведения.
- Каждый путь существует на диске. Путь, которого нет, Claude ищет сам и находит не всегда.
- Файл скилла в команде: `${CLAUDE_SKILL_DIR}/scripts/x.py`. Команда запускается из папки проекта, а не скилла.

## Оглавление

Файл длиннее 100 строк начинается с оглавления. Claude может открыть только начало файла и по нему решить, нужен ли он дальше. Всё, что ниже сотой строки, в этот момент для него не существует.

## Только то, чего Claude не знает

Исходное допущение: Claude уже очень умный. Про каждый абзац спроси: Claude действительно нужно это объяснение, оправдывает ли оно свои токены. «Что такое PDF» и «что такое API» вычёркивай. Проверка от противного: реши задачу без скилла, и всё, что Claude сделал верно сам, в скилле лишнее.

Объясняй причину правила, а не только приказывай. Капслок «ВСЕГДА» и «НИКОГДА» оставляй для хрупких операций, где ошибка дорого стоит.

## Свобода и петли проверки

Свобода зависит от хрупкости задачи. Узкий мост над обрывом: одна безопасная дорога, точные команды. Открытое поле: общее направление.

- Много верных путей: текстовые указания.
- Есть предпочтительный шаблон: скрипт или псевдокод с параметрами.
- Хрупко: точная команда, «не меняй флаги».
- Скрипт выполняется, а не читается: в контекст попадает только его вывод. Скрипт сам обрабатывает ошибки (создаёт файл по умолчанию, даёт запасной вариант), а не падает и не перекладывает это на Claude.
- Каждое число в скрипте обосновано комментарием. «Таймаут 47» без причины - ошибка.
- Массовое, необратимое: план в файл, проверка плана скриптом, выполнение, проверка результата. Сообщения скрипта проверки делай конкретными: «Поле X не найдено, доступные: A, B, C».
- Многошаговая работа: чек-лист, который Claude копирует и отмечает.
- Где важно качество: проверил, исправил, проверил снова, дальше только когда проверка прошла.

## Имя

Строчные латинские буквы, цифры, дефисы, до 64 символов, без XML-тегов, без слов `anthropic` и `claude`. Предпочтительно герундий (`processing-pdfs`, `writing-documentation`), допустимо существительное (`pdf-processing`) или глагол (`process-pdfs`). Один шаблон имён на всю коллекцию. Избегай `helper`, `utils`, `tools`, `documents`, `data`, `files`.

## Мелочи

- Не рассчитывай, что пакет установлен: рядом со скриптом строка вида `pip install pypdf`. На claude.ai пакеты ставятся из npm и PyPI, в Claude API сети и установки пакетов нет.
- Один термин на понятие: всегда «поле», не «поле/окошко/элемент».
- Никаких «до августа 2025 используй старый API». Устаревшее убери в раздел «Старые способы».
- Пути через `/`, не через `\`.
- MCP-инструменты полным именем `Сервер:инструмент`, иначе при нескольких серверах Claude может не найти инструмент.
- Не давай пять вариантов. Один по умолчанию, один запасной для особого случая.
- Копию скилла не храни в `~/.claude/skills/` или `.claude/skills/`: для Claude это ещё один скилл с тем же описанием.
- Конкретные примеры лучше абстрактных. Если качество зависит от стиля, дай 2-3 пары «вход - выход».

## Глазами: что скрипт не проверяет

1. Описание точно называет, когда применять, и в нём слова, которыми человек реально просит.
2. Нет объяснений вещей, которые Claude знает.
3. Нет разнобоя терминов.
4. Для хрупких операций точная команда, для гибких общие указания.
5. Нет пяти вариантов там, где нужен один.
6. Причины правил объяснены, а не только приказаны.
